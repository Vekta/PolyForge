# Dev Workflow Sync

PolyForge integrates with your project's real dev workflow: ticket transitions, local CI mirror, and parallel multi-ticket processing.

## Quickstart

### GitHub-only project

```bash
# In Claude Code, in your project root:
/forge
# Answers detection + parallelism questions. No Jira config needed.

# Then for any issue:
/smith #42
# → Branch created, implementation, local CI-mirror run, PR with Closes #42
```

### Jira-connected project

```bash
export JIRA_API_TOKEN=atlassian_api_token_xxx
export JIRA_EMAIL=you@company.com

/forge
# Additional 4 questions for transitions: onStart / onPrReady / onBlocked / onReject

# Work a ticket:
/smith DEV-123
# → Transition to "In Progress", implementation, CI-mirror, PR with DEV-123 prefix
# → Transition to "Code Review" on PR creation
```

### Multi-ticket parallel

```bash
/smith #10 #11 #12
# → Orchestrator plans 3 worktrees, CI-mirror sync once,
#   brainstorm questions serialized, agents spawn parallel
#   (test execution serialized if parallelism.mode=serialized).
```

## Configuration

All stored in `polyforge.json` (generated by `/forge`):

```json
{
  "schemaVersion": "1.1.0",
  "git": { "defaultBranch": "main" },
  "issueTracker": {
    "type": "jira",
    "config": { "projectKey": "DEV", "domain": "acme.atlassian.net" },
    "transitions": {
      "onStart":    { "status": "In Progress" },
      "onPrReady":  { "status": "Code Review" },
      "onBlocked":  { "status": "Blocked",  "requireComment": true },
      "onReject":   { "status": "Won't Do", "requireComment": true }
    }
  },
  "pipeline": {
    "ciMirror": {
      "source": ".github/workflows/ci.yml",
      "sourceHash": "sha256:abc123...",
      "commands": [
        { "name": "lint", "cmd": "npm run lint", "blocking": true, "origin": "workflow" }
      ],
      "learnedCommands": [],
      "excludePatterns": ["^deploy", "^release", "^npm publish"],
      "learningConsent": "granted"
    }
  },
  "parallelism": {
    "mode": "serialized",
    "reason": "docker-compose.yml with fixed ports 5432, 6379",
    "maxConcurrent": 3
  },
  "isolation": {
    "base_branch": "main",
    "base_ref": "origin/main",
    "worktree_root": "~/.polyforge/worktrees"
  }
}
```

## How each piece works

### Ticket transitions

- **GitHub issues**: PR body includes `Closes #{N}` only if PR target == `git.defaultBranch`. On non-default targets (e.g. merging to `develop`), body uses `Relates to #{N}` to avoid premature auto-close.
- **Jira**: at `/smith` and `/smith` start, transition to `onStart` status. On PR creation, transition to `onPrReady`. Stuck → terminal escalation (4 options).
- **TransitionId is resolved at runtime** via `GET /issue/{key}/transitions` — never stored. Robust to Jira workflow changes.
- **Partial failure** (PR created but Jira rate-limits): warn + continue. Never retry, never rollback. Flow always advances.

### CI mirror

- Parses `.github/workflows/*.yml` at `/forge` time, extracts blocking `run:` commands, resolves local composite actions (`./.github/actions/*`) recursively.
- Third-party actions (`uses: org/action@v1`) are flagged as warnings — their commands aren't mirrored but the **learning loop** covers them over time.
- Before each push, `_ci-mirror-sync` hash-gates: if `.github/workflows/` hasn't changed, no re-parse.
- `_ci-mirror-run` executes the stored commands sequentially. On failure, the skill auto-fixes (max 3 retries) before escalating.
- If no CI is detected, **fallback verbs** auto-detect from `package.json`/`composer.json`/`go.mod`/`pyproject.toml`/`Gemfile`/`Cargo.toml`.

### Learning loop

- When `/quench` runs on a failed CI, it extracts the failing command from `gh run view --log-failed`.
- If the command isn't already mirrored **and** matches no exclusion pattern, it's appended to `~/.polyforge/learned-commands.jsonl`.
- **Informed consent**: first time a command would be learned in a project, `AskUserQuestion` explains the mechanism. User chooses: Install routines + learn / Learn only / Skip this repo / Skip permanently.
- A nightly **learning-consolidator** routine (from PR #4 routines framework) reads the JSONL, dedupes by project, and opens a config PR per project adding the new commands to `pipeline.ciMirror.learnedCommands[]`. The PR uses `git pull --rebase` + semantic append-only merge to preserve any user edits.

### Parallel processing

- `/smith #10 #11 #12` (or `PROJ-xx` for Jira) triggers parallel mode.
- Orchestrator plans one worktree per ticket under `~/.polyforge/worktrees/{projectHash}/{fix|feat}/{id}/{timestamp}/`.
- `git fetch origin` runs once (reused by all worktrees).
- Pre-start brainstorm questions are asked **sequentially** — the orchestrator never poses two at once.
- Agents spawn up to `maxConcurrent` (defaults to `min(3, floor(cpus/2))`).
- If `parallelism.mode === "serialized"`, each agent acquires a global test lock (`~/.polyforge/ci-mirror.lock`, 15-min timeout) before running `_ci-mirror-run`. This prevents port collisions for projects with docker-compose or dev-server setups.

## Troubleshooting

### Jira transitions aren't happening

- Check `JIRA_API_TOKEN` and `JIRA_EMAIL` env vars are set in the shell where Claude Code runs
- `npx polyforge _fetch-jira-statuses --domain your.atlassian.net --project-key DEV` should return the list of statuses. If it errors, your token lacks `read:project` scope.
- Transitions are **no-op with warning** when Jira creds are missing — your flow won't fail, but nothing moves.

### Third-party GitHub Actions aren't mirrored

This is **defined behavior**, not a bug. The `/forge` parser flags them as warnings (`third-party-action`). Two mitigations:

1. **Automatic** — the learning loop catches them over time: next time CI fails on a command hidden in `uses: some-action/step@v2`, `/quench` learns it.
2. **Manual** — edit `polyforge.json` and add the command to `pipeline.ciMirror.commands[]` with `origin: "user-added"`. It will survive the hash-gated sync.

### Parallel mode unexpectedly serialized

- Check `parallelism.reason` in `polyforge.json` — the detector explains why (compose file, dev script, fixed port).
- Override with `parallelism.mode = "full"` if you're sure there's no actual shared service.
- If you're on pnpm <9, you may see a `pnpmWarning` field — upgrade or accept the serialization.

### Rate-limit window

- `--max-budget-usd` is the uniform budget gate for all users (subscription or API key)
- For Jira rate limits (429 responses), transitions warn and continue; the client does not retry (defined behavior to avoid amplification).

### The nightly learning-consolidator PR has conflicts

- It uses `git pull --rebase` + append-only semantic merge on `learnedCommands[]`. Conflicts should only happen if you've rewritten the entire `pipeline.ciMirror` section between two nights.
- If you see a conflict, resolve manually in the PR (it's labeled `routine:to-review` specifically so a human reviews it).

### First run in a new project with complex CI

Expected: the first `/smith` or `/smith` may push a PR that fails CI on a command that wasn't mirrored. `/quench` learns it, and the next run has full coverage. This is the designed pragmatic trade-off vs. trying to make the workflow parser exhaustive (which would require resolving every third-party action).

## CLI reference (internal subcommands)

Most users never call these directly — they're invoked by the skills. Listed for debugging:

| Command | Purpose |
|---|---|
| `npx polyforge _resolve-default-branch [<projectRoot>]` | Detects the default branch via `gh` or git |
| `npx polyforge _parse-workflows --project <p> --default-branch <b>` | Parses `.github/workflows/*.yml` |
| `npx polyforge _detect-parallelism [<projectRoot>]` | Detects parallel-safety |
| `npx polyforge _fetch-jira-statuses --domain <d> --project-key <K>` | Lists Jira project statuses |
| `npx polyforge _detect-migrations [<projectRoot>]` | Shows pending schema migrations |
| `npx polyforge _apply-migrations [<projectRoot>]` | Applies migrations (requires clean git) |
| `npx polyforge _jira-transition --domain <d> --key <K> --status <S> [--comment <text>]` | Transition a Jira issue |
| `npx polyforge _jira-comment --domain <d> --key <K> --body <text>` | Post a comment to a Jira issue |
| `npx polyforge _ci-mirror-sync --project <p> --default-branch <b>` | Hash-gated CI re-parse |
| `npx polyforge _ci-mirror-run --project <p>` | Run stored CI commands locally |
| `npx polyforge _ci-fallback-verbs --project <p>` | Auto-detect fallback commands |
| `npx polyforge _ci-learn --project <p> --pr <N>` | Learn failing CI command from a PR |
| `npx polyforge _parallel-plan --project <p> --kind fix\|feat --tickets "#10,#11"` | Plan a parallel run |
| `npx polyforge _parallel-create-worktrees --project <p> --plan '[...]'` | Create worktrees from a plan |
| `npx polyforge _test-lock-acquire --owner <name>` / `_test-lock-release` | Global test execution lock |

## Not in scope (v1)

- GitLab CI full support (parser is stubbed)
- Bitbucket Pipelines, Jenkins, CircleCI
- Jira Server / Data Center (only Jira Cloud API v3)
- Matrix coverage (runs one version locally, not N)
- Back-transitions on PR revert
- Linear / Height / ClickUp integrations
- Git hooks installed by PolyForge (use husky/lefthook independently)
